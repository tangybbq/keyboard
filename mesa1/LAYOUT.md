# mesa1 — reference geometry

Geometry recovered from `proto4/proto4-left`, which was originally an Eagle import.
Every switch position **and** every Edge.Cuts vertex in that board carries a constant
residual offset of **(+0.0011, +0.0036) mm**. Subtract it and the entire board lands on a
clean integer-millimetre grid.

```
integer_mm = proto4_coord - (0.0011, 0.0036)
```

Coordinates below are given in two forms:

- **abs** — integer mm in the proto4-left coordinate frame (raw minus the offset).
- **rel** — relative to the board origin, which we define as the top-left of the outline
  bounding box, `abs (82, 58)`. Use this frame for mesa1.

KiCad convention applies throughout: **+X is right, +Y is down.**

Board bounding box: **133 × 94 mm** (`abs` x 82..215, y 58..152).

## Switch grid — 12 keys

Standard Kailh Choc pitch: **18 mm columns × 17 mm rows**. Six columns, two keys each.

| LF1     |  91 |  83 |   9 | 25 | 0 | upper |
| LF2     |  91 | 100 |   9 | 42 | 0 | lower |
| L-STAR0 | 109 |  83 |  27 | 25 | 1 | upper |
| L-S0    | 109 | 100 |  27 | 42 | 1 | lower |
| L-T0    | 127 |  72 |  45 | 14 | 2 | upper |
| L-K0    | 127 |  89 |  45 | 31 | 2 | lower |
| L-P0    | 145 |  67 |  63 |  9 | 3 | upper |

| LS1     | 181 |  77 |  99 | 19 | 5 | upper |

### Column stagger

The whole grid is generated by a single per-column vertical drop. Column 3 (`P`/`W`) is the
highest; every other column is shifted down by the amounts below. Both keys in a column
share the same drop, and the two keys are always exactly 17 mm apart.

| col | rel X | drop (mm) |
|---|---|---|
| 0 |  0 | 16 |
| 1 | 18 | 16 |
| 2 | 36 |  5 |
| 3 | 54 |  0 |
| 4 | 72 | 10 |
| 5 | 90 | 10 |

> **The pinky columns (0 and 1) drop 16 mm, not 17 — this is intentional.** Confirmed from
> typing on the built proto4: the little finger clearly has less vertical reach than the
> others, so the pinky columns are deliberately staggered less than a full row.
>
> Treat 16 as a starting point rather than a settled value. Judging the *best* drop is hard
> because you acclimatise to whatever is in front of you within days, so short-term comfort
> is not evidence — the payoff is long-term ergonomics. Changing it between revisions is
> cheap; just don't expect first impressions to tell you much.

## Right-hand key names

The right bank is **not** a renaming of the left — these are steno key names, so the two
hands carry different keys. Names below are from `proto4-right`, matched to the left board
by grid position (proto4-right used identical coordinates, so the pairing is exact).

`mesa1 rel` is the mirrored position for mesa1-right, using `x' = 133 − x` about the
bounding-box centre at `rel x = 66.5`. **If the outline changes, the mirror axis changes and
these must be recomputed.**

| col | left ref | right ref | left rel | mesa1-right rel |
|---|---|---|---|---|
| 0 upper | LF1     | RD0  | (9, 25)  | (124, 25) |
| 0 lower | LF2     | RZ0  | (9, 42)  | (124, 42) |
| 1 upper | L-STAR0 | RT0  | (27, 25) | (106, 25) |
| 1 lower | L-S0    | TS0  | (27, 42) | (106, 42) |
| 2 upper | L-T0    | RL0  | (45, 14) | (88, 14)  |
| 2 lower | L-K0    | RG0  | (45, 31) | (88, 31)  |
| 3 upper | L-P0    | RP0  | (63, 9)  | (70, 9)   |
| 3 lower | L-W0    | RB0  | (63, 26) | (70, 26)  |
| 4 upper | L-H0    | RF0  | (81, 19) | (52, 19)  |
| 4 lower | L-R0    | RR0  | (81, 36) | (52, 36)  |
| 5 upper | LS1     | RS3  | (99, 19) | (34, 19)  |
| 5 lower | LS2     | RS4  | (99, 36) | (34, 36)  |

Column 5 is the **inner** column (nearest the thumbs, which sit at high X on the left
board); column 0 is the **outer** pinky column.

The right bank reads cleanly as steno pairs running inner → outer: `F/R` (col 4), `P/B`
(col 3), `L/G` (col 2), `T/S` (col 1), `D/Z` (col 0), with `RS3`/`RS4` as extra keys on the
inner column. Mirroring positions while keeping each name on its own column index therefore
lands `-D`/`-Z` on the right pinky, which is where they belong — the mirror does the right
thing without any renaming.

The left bank does **not** read as standard steno, and that is deliberate — see "Key
semantics" below. The one genuine error in proto4's naming is the thumb vowels, which are
labelled backwards on the right board.

## Matrix

Carried over from proto4. **5 columns shared across both halves; 3 rows per half.** The
RJ-45 carries exactly 8 conductors — `ROW_4/5/6` and `COL_A..COL_E` — so the left MCU scans
a 5 × 6 matrix covering all 30 keys. The right half has no MCU; its rows return over the
cable.

RJ-45 pinout (identical both ends): `P$1..P$3` = ROW_4/5/6, `P$4..P$8` = COL_A..COL_E.

MCU pins (mesa1-left): COL_A..E on `6, 7, A0, A1, A2`; ROW_1..3 on `0, 1, 2`;
ROW_4..6 on `3, 4, 5`. `A3` drives the RGB chain. That is 12 of the Tiny2040's 12 GPIO —
**fully allocated, no spares.**

### Assignment rule — by position, not by name

Keys in physical order (column-major, outer → inner, upper then lower, then thumbs
outer → inner), chunked into five groups of three. Group index gives the column, position
within the group gives the row.

**mesa1-left**

| | ROW_1 | ROW_2 | ROW_3 |
|---|---|---|---|
| COL_A | LF1 | LF2 | L-STAR0 |
| COL_B | L-S0 | L-T0 | L-K0 |
| COL_C | L-P0 | L-W0 | L-H0 |
| COL_D | L-R0 | LS1 | LS2 |
| COL_E | LNUM0 | L-A0 | L-O0 |

**mesa1-right** — same rule applied to its own (mirrored) geometry, so each key occupies the
mirror-image cell of its left-hand counterpart:

| | ROW_4 | ROW_5 | ROW_6 |
|---|---|---|---|
| COL_A | RD0 | RZ0 | RT0 |
| COL_B | TS0 | RL0 | RG0 |
| COL_C | RP0 | RB0 | RF0 |
| COL_D | RR0 | RS3 | RS4 |
| COL_E | RNUM0 | RU0 | RE0 |

> **This differs from proto4-right, deliberately.** proto4's right-hand rows run backwards
> relative to the left (its ROW_4/5/6 map to the left's ROW_3/2/1 by position) because that
> board was *flipped* rather than mirrored. mesa1 mirrors properly, so the rows run the same
> way on both halves. Firmware written against proto4 will need its right-hand row order
> reversed.

Diodes are cathode-to-row, anode-to-switch; switch other side to column.

## Key semantics — a steno variant, not standard steno

This is **not** a traditional stenotype layout, which is why several key names look wrong
against a standard steno chart. Recording the intent here so the irregularities are not
"corrected" by someone later.

### The left `S-` is split

Traditional steno has a single double-height `S-` key on the outer left. Here column 1 is
**two separate keys**, and that split is exploited:

| ref | col 1 | role |
|---|---|---|
| `L-STAR0` | upper | the **star** (`*`) |
| `L-S0` | lower | `S-` |

So `L-STAR0` is accurately named — it really is the star — it just lives where the upper
half of `S-` would be on a traditional machine.

### The traditional star position is repurposed

Column 5 is the innermost column on each hand — where a traditional machine puts the star.
Standard steno's star has poor ergonomics there, so those **four keys are custom modifiers**
instead:

| ref | hand |
|---|---|
| `LS1`, `LS2` | left, inner column |
| `RS3`, `RS4` | right, inner column |

Currently called **caret** and **plus** in steno terms. The two keys on a given hand are
**not currently distinguished** — both inner keys act as one — but the intent is to separate
them later. The wiring already gives each its own matrix cell, so that is a firmware change
only; no board revision needed.

The `S` in these names is a leftover from the star position's traditional neighbours; they
are not `S` keys.

### The left outer column is function keys

| ref | role |
|---|---|
| `LF1` | mode switch — **steno ↔ Taipo** |
| `LF2` | function key, best role **not yet settled** |

`F` here means *function*, not steno's `-F`. Note the hands are **not** semantically
mirrored: the left outer column is function keys while the right outer column is the
standard steno `-D` / `-Z` pinky pair.

### `NUM` is a thumb key, used as a modifier

`LNUM0` and `RNUM0` sit on the thumbs, one per hand. The Phoenix theory in use does not need
a number key, so `NUM` is kept as an **additional modifier to expand brief space**.

### The right bank is standard

`-F`/`-R`, `-P`/`-B`, `-L`/`-G`, `-T`/`-S`, `-D`/`-Z`, inner → outer. `TS0` is the `-S` key;
the `T` prefix is a naming quirk, not a `T` key.

### Consequence for the schematic

None of this affects wiring. The reference designators only need to be **stable and
consistent between schematic and PCB** — the steno meaning lives entirely in firmware, which
maps physical keys to chords. So the matrix can be built with these names as they stand; the
semantics above are documentation, not a constraint.

## Thumb cluster — 3 keys, rotated

Three keys in a straight line, same **18 mm** pitch, along a line **30° below horizontal**
(consecutive deltas are exactly `(18·cos30, 18·sin30) = (15.58846, 9.0)`). Each footprint is
rotated 60° in proto4.

Left hand, in raw proto4 coordinates. Left-to-right (increasing X) the order is
**LNUM, A, O**, i.e. `LNUM` is outermost and `O` sits nearest the centre of the keyboard.

| left ref | raw X | raw Y | raw rot | left rel |
|---|---|---|---|---|
| LNUM0 | 166.1184 | 121.3696 | 60° | (84.1173, 63.3660) |
| L-A0  | 181.7069 | 130.3696 | 60° | (99.7058, 72.3660) |
| L-O0  | 197.2953 | 139.3696 | 60° | (115.2942, 81.3660) |

### Right hand — proto4's vowel names are wrong, do not copy them

On the right board the correct left-to-right order is **E, U, RNUM**: `-E` nearest the
centre, `RNUM` outermost. `proto4-right` has these labelled `RNUM, RU, RE` left-to-right,
which is backwards; that file is not a usable source for thumb naming.

Mirroring the left cluster about `rel x = 66.5` produces exactly this order, so the pairing
is forced by the geometry rather than chosen:

| left ref | ↔ | right ref | mesa1-right rel | rot |
|---|---|---|---|---|
| L-O0  | ↔ | RE0   | (17.7058, 81.3660) | +30° |
| L-A0  | ↔ | RU0   | (33.2942, 72.3660) | +30° |
| LNUM0 | ↔ | RNUM0 | (48.8827, 63.3660) | +30° |

So the correspondence is **LNUM↔RNUM, A↔U, O↔E** — outermost to outermost, innermost to
innermost. On the right board the row ascends left-to-right (Y decreasing as X increases),
the mirror of the left board's descent.

These positions inherit the off-grid cluster origin noted above; once a clean anchor is
chosen for the left, re-derive the right by mirroring rather than editing these numbers.

The *spacing* is exact, but the cluster **origin is not on the mm grid** — subtracting the
board offset leaves `(166.1173, 121.3660)`, which is not a round number and does not appear
to be a rotation of any integer grid point about an obvious centre. The cluster origin is
therefore **TBD for mesa1**: pick a clean anchor and regenerate the three positions from it
rather than importing these values.

For reference, relative to the mesa1 origin the cluster currently sits at:

| ref | rel X | rel Y |
|---|---|---|
| LNUM0 | 84.1173 | 63.3660 |
| L-A0  | 99.7058 | 72.3660 |
| L-O0  | 115.2942 | 81.3660 |

## Footprint rotation: Eagle PG1350 vs. Kailh socket

proto4 uses the Eagle-imported `PG1350` footprint, whose alignment posts sit at
`(0, ±5.5)` — **vertical**. That is why every grid key in proto4 is placed at **90°**.

mesa1 will use `keyswitches.pretty/Kailh_socket_PG1350` (the hot-swap socket version, as
used in `jolt2/jolt2-verts`), whose alignment posts sit at `(±5.5, 0)` — **horizontal**,
matching the KiCad-standard Choc orientation. It is effectively the proto4 footprint
already rotated 90°.

So when transferring placements, **subtract 90° from the proto4 rotation**:

| | proto4 `PG1350` | mesa1 `Kailh_socket_PG1350` |
|---|---|---|
| 12 grid keys | 90° | **0°** |
| 3 thumb keys | 60° | **−30°** (= 330°) |

Note that `jolt2-verts` places its sockets at 90°, which is a *different* physical
orientation from proto4's 90° — do not copy that rotation value across.

The socket footprint is single-sided: pads 1 and 2 are on **B.Cu**, so the sockets mount on
the back of the board and the switches insert from the front.

## Board outline — mesa1 (current)

**This is the outline mesa1 uses.** It is the proto4 shape with the two part-specific
notches removed (they now live in their footprints' own `Edge.Cuts`) and five vertices
pushed outward so every socket pad clears the board edge. Still 133 × 94 mm.

Socket rotations are **not** the same on both hands — see below. The outline is fitted to
that specific combination.

| | rotation |
|---|---|
| mesa1-left grid (12 keys) | **180°** |
| mesa1-left thumbs (3 keys) | **−30°** |
| mesa1-right grid (12 keys) | **0°** |
| mesa1-right thumbs (3 keys) | **−150°** |

Worst-case pad-to-edge clearance across all 30 sockets on both boards: **+1.147 mm**
(LNUM0). This is the *only* rotation combination that clears — see `DESIGN.md`.

13 vertices, traversal order, all whole mm:

```
(0,16) (55,0) (71,0) (108,8) (133,8) (133,70) (119,94)
(70,65) (79,50) (61,41) (38,41) (38,51) (0,51)
```

Five vertices moved outward from the proto4 shape to make room for the sockets:

| | proto4 | mesa1 |
|---|---|---|
| 7  | (71, 66) | (70, 65) |
| 8  | (80, 51) | (79, 50) |
| 9  | (59, 40) | (61, 41) |
| 10 | (36, 40) | (38, 41) |
| 11 | (36, 51) | (38, 51) |

Vertices 7–8 open up the thumb diagonal; 9–11 shrink the bottom-left notch, which was
fouling the column-1 lower key on both hands.

`mesa1-Edge_Cuts.dxf` holds this outline. Import via **File → Import → Graphics**, layer
**Edge.Cuts**, placed at **(100, 50)**, line width 0.1 mm. KiCad imports it as a *group* —
**Edit → Group → Ungroup** afterwards or the segments cannot be edited individually.

## Right hand — proto4 was *not* mirrored

Worth being explicit about, because mesa1 changes this.

`proto4-right` has **identical** switch coordinates to `proto4-left` — not mirrored, the same
numbers. Its outline is also identical except that four vertices are missing: `(195,66)`,
`(195,84)`, `(207,84)`, `(207,66)`. Those four are the 12 × 18 mm tab described above, so on
the right board that edge runs straight from `(190,66)` to `(215,66)`. The tab is a
left-board-only feature, which lines up with the left board being the one carrying the MCU.

`proto4/proto4-duplex` is the same grid shifted +0.5 mm in X. **It was never fabricated** —
it carries 3 LEDs where every built board has 4 — so treat anything found only in duplex as
unproven. `proto4-left` is the board that exists.

**mesa1 mirrors the right hand instead.** See `DESIGN.md` for the transform and its
consequences for the socket footprint.
